# 扫码配对的安全现状与加固建议

> 记录时间：2026-10-27 · 面板 3.6.143 / APP 3.7.100
> 结论先行：**二维码是明文编码，不是加密。**
> 本文最初（2026-10-27 上午）只做记录、不改代码；当天下午已实施**档 1**：
> 二维码改为 120 秒**一次性票据**，APP 用票据换**设备令牌**（3.6.144 / APP 3.7.101）。
> 下面保留当时的原始评估，并标注哪些已落地。

## 一、一句话结论

二维码里装的是 `{"i":"<地址>","t":"<token>"}` 的**明文 JSON**，任何扫码 App 都能直接读出；
token 是 `config.json` 里的**长期单一凭据**，没有过期、没有一次性、没有轮换入口。
它的安全性完全依赖"码不被第三方看到"这一条假设，以及 token 本身不被泄露。

## 二、当前机制（数据流）

```
面板浏览器                    服务端                      手机 APP
    │                           │                            │
    ├─ GET /api/pair/info ─────►│ 探测可达地址               │
    │◄─ url/token/canPair ──────┤ routes/pair.py:37          │
    │                           │                            │
    ├─ GET /api/pair/qr ───────►│ 生成 SVG 二维码            │
    │   (X-Token)                │ 内容 {"i","t"}             │
    │◄─ image/svg+xml ──────────┤ routes/pair.py:56 / :61    │
    │                           │                            │
    │  每 60s 重算一次（panel.js:223）                        │
    │                           │       扫码 ────────────────►│ parsePairPayload
    │                           │◄──── 握手 /api/config ──────┤ QrConnect.kt:49
```

要点：

* **服务端无状态**：每次请求现算地址（`services/pair_target.py`），不保存任何配对会话。
* **二维码无时效**：一张码只要地址与 token 不变就永久有效，截图存下来几个月后仍能连。
* **60 秒刷新不是"续期"**：目的只是吸收环境变化（隧道断了、端口没在听、IP 变了），
  内容不变时也会整块重绘 SVG。
* **不可达时不出码**：`canPair=false` 时 `/api/pair/qr` 返回 409，前端只显示提醒
  （`pair_target` 绝不把 127.0.0.1 编进码里）。

## 三、威胁模型

本文只讨论以下三类攻击者；公网无差别扫描不在其中（需要端口暴露 + 无 token 同时成立，
而正常启动路径已被强制生成 token，见第五节）。

| 编号 | 攻击者 | 能力假设 |
|---|---|---|
| A | 物理接近者 | 能看到屏幕、能拍照/截图/录屏、能肩窥 |
| B | 同一网段 / 同一 Tailnet 的其他设备 | 能访问 8766 端口，但没有 token |
| C | 拿到 `config.json`（或备份包）的人 | 能读到 token 明文 |

## 四、风险清单

| 编号 | 风险 | 触发条件 | 影响 | 现状缓解 | 等级 |
|---|---|---|---|---|---|
| R1 | 二维码明文包含**长期** token | 拍照 / 截图 / 录屏 / 投屏 | 拿到码 = 永久拿到完整访问权（读写、删除、备份下载、爬虫） | 码只在面板弹窗展示；`/api/pair/qr` 需 `X-Token` | **高** |
| R2 | 无时效、无一次性 | 截图留存 | 几个月后仍然有效，无法判断是否被用过 | 无 | 中高 |
| R3 | **无签名，码可伪造** | 攻击者让用户扫自己的二维码 | APP 会把地址与 token 填成攻击者的，连到恶意服务器并交出凭据 | 无（仅靠用户判断来源） | 中 |
| R4 | 传输为 **HTTP 明文**（`AndroidManifest.xml:15` `usesCleartextTraffic="true"`） | 走局域网 IP、或 http 穿透域名 | 同链路者可截获 `X-Token` | 走 Tailscale（100.x）时链路有 WireGuard 加密；**3.6.148 起再叠一层 TLS**：`tailscale serve` 在 443 用 Let's Encrypt 证书终结，手机走 `https://<节点>.ts.net` | **低**（经 443 已加密；8766 明文端口仍在，需令牌） |
| R5 | token **无法轮换** | 怀疑泄露 | 只能手改 `config.json` + 重启面板，成本高、易拖延 | 无（无轮换端点） | 中 |
| R6 | token 为空时**全部放行**（`app.py:379` `if not token: return None`） | 非常规启动（直接用 flask 跑、或绕过 `services/server.py`） | 完全无鉴权 | `services/server.py:99 _ensure_remote_token` 在非本机监听时自动生成并持久化；`launcher_core.ensure_remote_token` 亦然 | 低（条件性） |
| R7 | 本机回环**免鉴权**（`app.py:382`） | 本机任意进程 / 本机浏览器脚本 | 可读取 token | 有意的设计：远程进程虽绑 `0.0.0.0`，但回环只有本机能到达 | 低（本机可信前提） |

## 五、已经做了的保护（别只讲风险）

1. **远程绑定强制 token**：`services/server.py:99 _ensure_remote_token()` —— 非本机监听且
   token 为空时，自动生成 `bks-` + 24 位十六进制并写回 `config.json`，杜绝 `0.0.0.0` 裸奔。
   启动器路径同样有 `launcher_core.ensure_remote_token()`。
2. **接口鉴权**：`app.py:373 _token_gate()`，除页面壳与三个取图端点外都要 `X-Token`
   或 `?token=`；比较用 `secrets.compare_digest`（恒时，避免时序侧信道泄露前缀）。
3. **二维码端点非公开**：`/api/pair/info` 与 `/api/pair/qr` 都不在 `PUBLIC_ENDPOINTS` 里
   （内容即 token，凭 token 才能取）。
4. **不编回环地址**：`pair_target.detect()` 无可用地址时 `ok=False`，`/api/pair/qr` 返回 409，
   前端不请求、不出码——避免"扫了必然连不上"。
5. **地址探测只读**：不启动任何进程、不改配置，只用进程表 + 网卡 + TCP 探测。

## 六、加固建议（**三档均已落地**：档 1 → 3.6.144、档 2 → 3.6.145、档 3 → 3.6.146）

### 档 1：一次性短时效票据（✅ 3.6.144 已实现）

* 码内容改为 `{"i":"<地址>","p":"<32 字节随机票据>"}`，**不再带长期 token**。
  （已实现；有效期取 **120 秒**而非 60 秒——首次绑定要「安装 → 授权相机 → 对准」，
  60 秒实测偏紧，`config.json` 的 `pair_ticket_ttl` 可调，夹在 30~600。）
* 新增 `POST /api/pair/claim`：用 `p` 换设备令牌。`p` 有效期 120 秒、**首次使用即作废**、
  记录来源 IP；来源变化则拒绝。
* APP 侧 `parsePairPayload` 兼容新旧两种格式（有 `p` 走 claim，无 `p` 走旧的 `t`）。
* 改动面：`routes/pair.py`、`services/pair_target.py`（不变）、`QrConnect.kt`、新增设备令牌存储。
* 收益：即使码被拍到，窗口只有两分钟且一次有效。

### 档 2：档 1 + 令牌轮换与设备管理（✅ 3.6.145 已实现）

* 已实现 `POST /api/config/rotate-token`（二维码弹窗里的「轮换访问令牌」），
  生成新 token、写回 `config.json` 与内存 `CFG`，并写进当前浏览器，免得自己把自己锁在外面。
* **注意与档 1 的差异**：轮换主令牌**不会**让已扫码的 APP 掉线——它们用 `dev-` 设备令牌。
  受影响的只有仍在用主令牌的客户端（远程网页）。
* 已实现设备管理：`GET /api/pair/devices` 列出、`DELETE /api/pair/devices/<id>` 单台吊销。
  这才是"设备令牌"相对单一主令牌的核心收益——旧手机丢了只踢那一台。
* 仍未做：轮换的审计日志（谁在什么 IP 下换的）。

### 档 3：防伪造（TOFU + 挑战-响应）+ 链路提示（✅ 3.6.146 已实现，方案有调整）

* **方案调整**：原计划的"码内附 HMAC 签名"没做——公钥必须先到手机上（只能烧进 APK，
  换服务器就要重出包），而下面这套同样能防假服务器且无需预置。
* **实际做法：TOFU + 对称挑战-响应**。服务器在 `_state/server_identity.json` 生成一次
  32 字节 `secret`；APP 首次 claim 时记在手机上；以后每次配对前发随机 nonce，
  服务器回 `HMAC-SHA256(secret, nonce)`，APP 用记下的 secret 验。
  假服务器没有 secret，**答不出 proof** → 拦下。
* **为什么不是"比对指纹字符串"**：指纹只是 info 里的一个字符串，假服务器照抄就过了，
  挡不住任何东西。它只保留为"给人核对的显示值"。
* 面板在二维码弹窗里显示链路：`🔒 经 Tailscale 隧道加密` / `HTTPS` /
  `⚠ HTTP 明文（同网段可能被截获，建议改用 Tailscale）`，并显示服务器指纹。
* **局限（必须承认）**：首次配对时手机里没有 secret 可比，**无法判断真假**——这是所有
  TOFU 方案的固有边界。本档防的是"配对过一次之后被换成另一台机器"
  （DNS 劫持、码被替换、地址被改），不防"第一次就扫到假码"。
* 换服务器后 attest 必然对不上，所以设置页有「清除服务器身份校验」入口，否则会把自己锁死。

### 不建议的做法

**给二维码"加密"**：密钥必须通过另一条信道交给 APP；若密钥也放在码里就自相矛盾。
而"看到码的人"往往也能看到屏幕（威胁模型 A），加密收益有限。**时效 + 一次性 + 可吊销**
才是缩窄窗口的正解。

## 七、今天就能做的运维措施

1. **怀疑泄露就轮换**：改 `config.json` 的 `token` → 重启面板 → 所有设备重新扫码。
   轮换后旧码与旧 token 立即失效（APP 会报"需要访问令牌"）。
2. **不要在相册/聊天工具里长期保留二维码截图**；用完删掉。
3. **不要直接把 8766 暴露到公网**；优先走 Tailscale 内网（链路已由 WireGuard 加密）。
4. **确认 token 非空**：`curl -s http://127.0.0.1:8766/api/pair/info` 看 `token` 字段长度
   （正常为 `bks-` + 24 位 = 28 字符）。

  * `/api/pair/info` 不再返回主令牌；`/api/pair/claim` 进公开端点（靠票据本身鉴权）；

  R3（码可伪造）与 R4（HTTP 明文）留给档 3。

* **2026-10-27**：用户选择"先不改，只记录风险"。理由：本项目是个人本地文库，
  威胁模型主要是"手机被他人拿到 / 码被拍到"，不是公网攻击者；投入应与风险匹配。
  若后续发生凭据泄露、或需要把服务开放给更多设备，再按档 1 → 档 2 → 档 3 逐步实施。

* **2026-10-27（夜，3.6.147）**：**删除主令牌**。用户手机已用设备令牌，主令牌成了唯一
  剩下的静态凭据。删之前先修了两个问题：
  1. `_token_gate` 是 **fail-open**（主令牌为空 → 放行一切），"删主令牌"会直接把 8766
     变成无鉴权端口。已改为 fail-closed：回环与公开端点放行，其余只认主令牌或设备令牌；
  2. 两处启动逻辑（`services/server._ensure_remote_token`、`launcher_core.ensure_remote_token`）
     原本会在 token 为空时自动生成，会把删掉的令牌悄悄补回来。现在"已有配对设备"时不生成。
  * 现状：`config.json` 无主令牌，鉴权只靠设备令牌；远程网页需在本机点「生成访问令牌」才能再用。
  * `compare_digest("", "")` 返回 True 的坑也一并挡住（`token and`）。

* **2026-10-27（夜，3.6.148）**：**关掉 R4**——远程访问改走 HTTPS，但**不在 Flask 里做 TLS**。
  * 为什么不用自签证书：Android 默认拒绝自签 CA，必须给 APP 加 cert pinning + 证书分发/续期，
    为一个个人文库维护一套 CA 不划算；
  * 为什么不用公网 CA 手配：动态家宽 + CGNAT，HTTP-01/DNS-01 验证都做不了；
  * 选 **Tailscale serve**：tailscaled 自己向 Let's Encrypt 申证书并自动续期，
    `issuer=C=US, O=Let's Encrypt, CN=YE2` —— **公共信任链，Android 系统默认认可，
    APP 一行不用改**；443 上终结 TLS 后反代到 `127.0.0.1:8766`。
  * 代码侧只改"识别"（详见 CHANGELOG 3.6.148）：
    `_scheme()` 判外部协议（`X-Forwarded-Proto` **只信回环来源**，否则同网段可伪造头
    让人谎报"已加密"）、https 地址**不补 `:8766`**、`_link()` 针对二维码里那个地址而不是当前页面。
  * 顺带查出 `pair_url` / `pair_ticket_ttl` 从未进入 `common._apply_scalars` 白名单 ——
    **"设置 pair_url 后重启"这条建议此前一直是空指令**（写了也不生效、且不报错）。
  * **本次最大的意外**：HTTPS 第一版上线后，`GET https://<节点>.ts.net/api/library`
    **不带令牌返回 200 与 554 KB 全量数据** —— 加加密层反而把鉴权弄没了。
    两层原因：① tailscaled 恒从 `127.0.0.1` 反代，`_token_gate` 判"回环免鉴权"
    把 tailnet 内每台设备都当成本机；② waitress 默认 `clear_untrusted_proxy_headers=True`
    且 `trusted_proxy=None`，把所有 `X-Forwarded-*` 清掉，后端连真实客户端都看不到。
    修法：新增 `services/netaddr.py` 统一"真实客户端"判定 + `_make_server` 配
    `trusted_proxy="127.0.0.1"`（只信本机进程注入的头）。同样的问题在
    `panel/images.py:client_wants_low` 里还有一处（低带宽判定失效），一并修了。
  * R4 现状：**经 443 的链路已加密且可验证**；8766 明文端口仍在，仅受令牌保护。
    彻底收掉见下方「可选加固」。

## 可选加固：把远程服务收回回环

443 已经能进之后，8766 的 `0.0.0.0` 绑定就是最后一条明文路径。改成只绑回环：

```bash
# 启动器里把远程模式改成 --host 127.0.0.1（launcher_proc.remote_launch 的 _spawn 参数）
# 或直接手工起：
python app.py --host 127.0.0.1 --port 8766 --no-browser
```

* **收益**：tailnet 内和局域网内都不再有明文监听，只剩 `https://<节点>.ts.net` 一个入口，
  且该入口无法被同网段设备看到（随 tailnet ACL 走）。
* **代价**：局域网直连（`http://192.168.x.x:8766`）失效；`pair_target` 的隧道 IP 探测会
  全部落空，二维码只能靠 `config.json` 的 `pair_url`（本次已配好，不受影响）。
* **建议**：如果只在这台机器上用手机访问，值得改；如果还要给局域网平板/电视用，维持现状。
